# 市场全景功能设计与 AI 提示词方案 V2.0

> 功能正式名称：**市场全景**  
> 默认观察窗口：**最近 120 个自然日**；只纳入其中实际存在的交易日复盘。若历史不足 120 天，则使用当前已有的全部复盘。  
> 适用项目：个人交易决策支持系统 / A股复盘模块  
> 目标读者：AI Coder、后端开发、前端开发、Prompt 工程  
> 版本：V2.0

## 0. 核心定位

“市场全景”不是当前市场状态卡，也不是最近几份日报的摘要。

它的核心任务是：

> **站在今天，回看默认最近 120 天，讲清楚这一段市场是怎样一步一步演进到今天的。**

用户每天都会看每日复盘，因此并不缺“今天谁强、今天谁弱、明天看什么”。真正会随时间遗忘的是：

- 一个月前市场处于什么阶段；
- 两个月前主导市场的故事是什么；
- 一个故事是怎样启动、扩散、分歧、退潮、再启动的；
- AI、医药、农业、贵金属、化工、券商等方向之间如何接力；
- 市场偏好怎样从大票切到小票、从趋势切到连板、从容量切到高价格反应；
- 哪些重要节点真正改变了后面几十天的市场；
- 当前究竟处在过去 120 天历史中的什么位置。

所以 V2.0 的核心表达是：

> **纵轴 = 时间阶段；横轴 = 重要市场故事。**

市场全景必须同时把这两条线讲清楚。


# 1. V1.0 的问题与 V2.0 的改造目标

V1.0 把市场全景设计得过于接近“当前作战地图”，导致生成文章大量围绕：

- 当前市场状态
- 当前资金偏好
- 当前赚钱效应
- 当前亏钱效应
- 当前核心观察股
- 当前未决问题
- 本次更新

这些内容主要属于“每日复盘 / 当前监控”，不是市场全景的主体。

V2.0 必须完成以下改造：

1. **从“当前状态”转成“历史演进”。**
2. **从 Active Story 转成整个窗口内的重要 Story。**
3. **保留已经退潮但曾经重要的故事。**
4. **Story / Episode 继续保留，但仅作为后台历史结构，不直接作为文章卡片。**
5. **大型母题必须讲内部子主题如何迁移。**
6. **前台文章必须有叙事，不允许直接 dump 数据库字段。**
7. **当前只作为全文最后 5%～10% 的终点说明。**
8. **每天增量更新结构化历史，但前台每次重新渲染整个窗口，不做“旧文章+今日日报”的递归摘要。**


# 2. 时间窗口

默认：

```text
window_days = 120
window_type = calendar_days
```

例如截至 2026-08-31：

```text
requested_start_date = 2026-05-04
end_date = 2026-08-31
```

如果系统实际上只有 2026-08-04 至 2026-08-31 共 16 个交易日复盘，则必须明确：

> 当前历史数据不足默认 120 天，本次市场全景基于现有 16 个交易日复盘生成。

不能补造缺失历史。

后续可扩展：

```text
30天 / 60天 / 120天 / 180天 / 自定义
```

但产品名称始终只叫：

> **市场全景**


# 3. 市场全景必须回答的十个问题

1. 过去这段时间，市场大体经历了哪些阶段？
2. 每个阶段的指数、成交、广度、风险偏好和主导风格是什么？
3. 一个阶段为什么结束，另一个阶段为什么开始？
4. 过去 120 天最重要的市场故事有哪些？
5. 每个重要故事是如何演进的？
6. 同一个故事是否经历了多轮独立行情？
7. 资金偏好在这段时间如何变化？
8. 哪些日期是真正改变市场结构的转折点？
9. 不同故事之间如何接力、竞争、共振或独立运行？
10. 截至窗口末端，我们现在处在整段历史的什么位置？


# 4. 前台文章不应该再有的独立章节

市场全景文章原则上删除：

- 当前市场一句话（可以融入第一章开头，但不能成为文章主体）
- 当前赚钱效应
- 当前亏钱效应
- 核心观察股
- 明日验证
- Open Questions
- 本次更新相较上一版
- 正面证据 / 负面证据
- Priority / Confidence / State 卡片

这些信息如果系统其他模块需要，可以继续保存在后台，但不要渲染进市场全景正文。

原因：

> **市场全景是历史叙事，不是当前交易看板。**


# 5. 第一层数据模型：Market Phase

## 5.1 定义

Market Phase 表示窗口内一个相对稳定的市场环境阶段。

120 天通常只应划分：

```text
4 ~ 8 个主要阶段
```

特殊情况下：

```text
3 ~ 10 个
```

如果生成 20 个以上阶段，说明模型在做日记而不是全景。

## 5.2 阶段切换依据

至少应出现若干市场级变化：

- 风险偏好显著改变
- 成交量级改变
- 市场广度显著改变
- 主导风格改变
- 主线形成或退潮
- 高位赚钱效应显著改变
- 市场级风险释放
- 新母题接替旧母题

不能因为一个板块一天涨停就新建阶段。

## 5.3 示例结构

```json
{
  "phase_id": "PHASE_20260819_01",
  "start_date": "2026-08-19",
  "end_date": "2026-08-20",
  "title": "风险快速释放与恐慌后修复",
  "summary": "市场从结构轮动突然进入全面风险释放，随后次日缩量止血。",
  "index_environment": "先大跌后修复",
  "liquidity": "放量杀跌后缩量修复",
  "breadth": "极弱后改善",
  "risk_appetite": "急降后止血",
  "dominant_styles": ["防御", "低位修复"],
  "dominant_story_ids": ["PHARMA", "PRECIOUS_METALS"],
  "ending_reason": "第一轮恐慌释放完成，市场进入新的结构修复。",
  "important_dates": ["2026-08-19", "2026-08-20"]
}
```


# 6. 第二层数据模型：Story

Story 是资金在一段时间内围绕共同逻辑反复交易的“故事”。

不是软件行业标签。

例如：

```text
AI
PHARMA
AGRICULTURE
PRECIOUS_METALS
CHEMICALS
BROKERAGE_FINANCE
REAL_ESTATE
ROBOTICS
CONSUMPTION
```

## 6.1 是否进入市场全景的标准

不是看它今天是否 Active。

而是看：

> **它在这 120 天中是否重要到足以帮助理解整段市场历史。**

以下都可以进入：

- 当前仍活跃；
- 已经退潮但曾经主导市场；
- 形成过明显赚钱效应；
- 影响过风险偏好；
- 持续较长；
- 有多轮 Episode；
- 对其他故事产生明显接力关系。

推荐重要性：

```text
major
important
secondary
minor
```

`major` 和 `important` 才进入主文；`minor` 仅后台保存。


# 7. Episode：同一个 Story 的一轮独立资金周期

`story_id` 表示长期故事。

`episode_id` 表示这一轮行情。

例如：

```text
story_id = AGRICULTURE
episode_id = AGRICULTURE_20260817_01
episode_id = AGRICULTURE_20260824_02
```

第一轮可能：

> 8/17启动 → 8/18扩散 → 8/19集中 → 8/21退潮。

第二轮可能：

> 8/24新天气变量重新启动 → 8/25确认 → 8/27再扩散 → 8/31高位缩圈。

## 7.1 什么时候必须创建新 Episode

如果上一轮已经：

```text
retreat
retired
```

后来因：

- 新天气变量
- 新价格变量
- 新产业变量
- 新政策变量
- 新事件

重新形成群体攻击，则必须新建 Episode。

禁止把两轮独立行情写成“从第一次启动一直持续至今”。


# 8. State Node：后台压缩历史，不直接用于文章

建议状态枚举：

```text
watch
new_launch
strengthening
expanding
confirmed
divergence
core_concentration
repair
re_strengthening
high_level_concentration
weakening
retreat
retired
```

例如后台：

```json
[
  {"date":"2026-08-24","state":"new_launch","summary":"新天气变量重新激活农业。"},
  {"date":"2026-08-25","state":"confirmed","summary":"完成第一次跨日确认。"},
  {"date":"2026-08-27","state":"re_strengthening","summary":"板块重新扩散。"},
  {"date":"2026-08-31","state":"high_level_concentration","summary":"最高核心继续，后排开始亏钱。"}
]
```

前台必须改写成自然叙事：

> 农业在8月24日被新的极端天气预期重新激活，25日即完成第一次跨日确认。26日资金开始向前排集中，但27日并未进一步衰减，反而重新扩散。到了31日，最高核心仍然穿越，但后排开始明显亏钱，第二轮行情由扩散进入高位缩圈。

禁止直接写：

```text
状态：high_level_concentration
证据：
负面证据：
下一验证：
```


# 9. 大型母题的 Subtheme 设计

AI、医药等大型母题不能只保存一个 Story Summary。

必须允许保存内部主要子主题的历史角色。

例如 AI：

```json
[
  {
    "subtheme_id": "AI_CPO",
    "display_name": "CPO / 光通信",
    "first_major_date": "2026-08-14",
    "role_summary": "AI早期重要容量承载，后续经历明显兑现。"
  },
  {
    "subtheme_id": "AI_LIQUID_COOLING",
    "display_name": "液冷",
    "role_summary": "AI硬件分歧后持续性较强的新承载。"
  },
  {
    "subtheme_id": "AI_APPLICATION",
    "display_name": "AI应用",
    "role_summary": "窗口后段由商业化事件推动，从边缘走向市场前台。"
  }
]
```

如果复盘中确实存在：

- 芯片
- CPO
- PCB
- 存储
- 液冷
- PTFE
- 超节点
- AI应用

文章必须讲清楚：

> 哪个先出现、哪个成为容量承载、哪个退潮、哪个接棒，以及这是母题结束还是内部换承载。

不能只讲最近几天。

```json
  "story_interactions": [],
  "window_patterns": [],
  "window_end_state": {},
  "source_reviews": [],

}
```

## 10.1 window

```json
{
  "window_days": 120,
  "window_type": "calendar_days",
  "requested_start_date": "2026-05-04",
  "actual_first_review_date": "2026-08-04",
  "end_date": "2026-08-31",
  "review_count": 16,

```

## 10.2 story 示例

```json
{
  "story_id": "PHARMA",
  "display_name": "医药",

  "first_seen_in_window": "2026-08-13",

  "episodes": [],

}
```

其中 `representative_stocks` 仅表示历史角色，不是“明日观察股”。


# 11. Turning Point

Turning Point 是真正改变后续市场理解的重要节点。

不是普通涨跌。

结构：

```json
{
  "date": "2026-08-27",
  "title": "AI母题级重新强化",
  "before": "AI此前主要处于分支修复，容量核心未完全同步。",
  "event": "英伟达财报超预期，A股AI硬件多分支共振。",
  "after": "风险偏好升级，AI重新成为第一进攻母题。",
  "affected_story_ids": ["AI"],
  "importance": "major"
}
```

每个 Turning Point 必须能回答：

1. 此前是什么状态？
2. 实际发生了什么？
3. 为什么它不是普通波动？
4. 后续市场因此发生了什么变化？

默认 120 天只保留约：

```text
8 ~ 15 个
```


# 12. Style Evolution：记录“变化过程”，不是“当前偏好”

固定维度建议：

- 大票 vs 小票
- 趋势 vs 连板
- 高位 vs 低位
- 容量 vs 高价格反应
- 10cm vs 20cm / 30cm
- 成长 vs 防御 / 周期
- 主线集中 vs 快速轮动

结构示例：

```json
{
  "large_vs_small": {
    "summary": "窗口早段……，中段……，后段……",
    "nodes": [
      {
        "date": "2026-08-19",
        "state": "small_caps_under_pressure",
        "summary": "..."
      }
    ]
  }
}
```

文章必须写成：

> 早期 → 中段 → 后段 → 窗口末端

不能只写：

> 当前偏小票。


# 13. Story Interaction：把故事连起来

市场全景不能把每个 Story 写成孤立积木。

必须记录重要关系，例如：

```json
{
  "date_range": "2026-08-18/2026-08-21",
  "story_ids": ["AI", "AGRICULTURE", "PHARMA"],
  "relationship": "rotation",
  "summary": "AI分歧期间农业相对强化，医药从高潮进入分歧。",
  "confidence": 0.78
}
```

允许关系：

```text
rotation
coexistence
competition
risk_off_reallocation
mother_theme_rotation
independent_trend
```

注意：

不能写：

> “A的钱流到了B。”

除非有真实账户数据。

只能写：

> 市场重心从 A 转向 B；
> B 在 A 分歧期间相对强化；
> A 与 B 同时共振。


# 14. Window Pattern：这段历史反复出现的规律

只保存 3～8 条。

例如：

```json
{
  "pattern_id": "PATTERN_01",
  "summary": "新方向第一日强度不如第二日是否继续给予参与者正反馈重要。",
  "supporting_cases": [
    "农业8/24→8/25",
    "固态电池8/24→8/25",
    "核聚变8/26→8/27"
  ]
}
```

这些规律必须来自窗口内真实反复出现的案例。

不能把通用交易格言硬塞进去。


# 15. 市场全景文章固定结构

前台文章标题始终：

```text
# 市场全景
```

可以在标题下写：

> 观察窗口：最近120天；实际覆盖：2026-08-04 至 2026-08-31，共16个交易日复盘。

正文固定八章。

## 第一章：过去这段时间，市场走了一条什么路

全文 8%～12%。

连续叙事，先给用户一条完整历史主线。

不要表格。
不要当前状态卡。

## 第二章：市场阶段演进

全文 20%～25%。

按 Phase 时间顺序写。

每个阶段回答：
- 环境
- 成交
- 广度
- 风险偏好
- 风格
- 主导故事
- 为什么结束

## 第三章：主要市场故事演进

全文 35%～45%，是最重要章节。

按整个窗口的重要性排序，不按当前强弱排序。

大型母题必须讲内部子主题如何迁移。

已经退潮但曾重要的故事也必须完整写。

## 第四章：资金风格如何变化

全文 10%～15%。

必须讲变化过程，不是当前标签。

## 第五章：最重要的市场转折点

选真正的重要节点。

写：
此前 → 发生 → 改变 → 后续。

## 第六章：主线之间如何接力、竞争和共振

把故事连成一张历史关系网。

## 第七章：回头看，这段市场反复出现了什么规律

3～8 条。

## 第八章：截至窗口末端，我们现在走到了哪里

全文仅 5%～10%。

当前只是历史终点，不是全文中心。


# 16. 前台文风要求

市场全景应该像：

> **一个真正理解市场历史的人，在给另一个交易者讲这 120 天发生了什么。**

必须使用连续叙事：

- 起初……
- 随后……
- 到了……
- 但……
- 真正的转折发生在……
- 此后……
- 与此同时……
- 到窗口后段……

避免机器化字段：

```text
状态：
Priority：
正向证据：
负向证据：
下一验证：
核心传感器：
```

后台结构化，前台自然语言。

允许长段落，但不能写成一百个 bullet。

不追求文学腔，但必须：

> 清楚、连续、有时间感、有转折、有因果、有可读性。


# 17. 全量重建流程

输入：

> 默认最近120个自然日内的全部原始独立复盘。

历史不足则全部读取。

流程：

1. 按日期排序全部复盘。
2. 提取每天的市场级环境和重要故事。
3. 划分 Market Phase。
4. 建立 Story。
5. 对同一 Story 拆分 Episode。
6. 提取大型 Story 的 Subtheme 演进。
7. 识别 Turning Point。
8. 生成 Style Evolution。
9. 生成 Story Interaction。
10. 生成 Window Pattern。
11. 生成 Window End State。
12. 输出 `market_panorama_history.json`。
13. JSON Schema 校验。
14. 使用独立叙事渲染 Prompt 生成 `market_panorama.md`。
15. 使用 Reviewer 检查生成质量。
16. Reviewer 不通过则重新生成文章。


# 18. 全量重建 Prompt V2

```text
你是一名专业的A股市场历史复盘分析器。

你现在要维护的功能叫“市场全景”。

默认观察最近120个自然日。如果提供的复盘不足120天，只能基于现有复盘，不得补造缺失历史。

你的任务不是总结今天，也不是把最近几份日报拼起来。

你的任务是：站在窗口末端，重新理解整个时间窗口中：

- 市场经历了哪些阶段；
- 主线和重要故事怎样演进；
- 不同故事如何接力、竞争、共振；
- 资金风格怎样变化；
- 哪些日期是真正的转折；
- 最终是怎样一步一步走到窗口末端的。

【市场全景不是】

- 当前市场状态卡
- 当前赚钱效应
- 当前亏钱效应
- 核心观察股列表
- 明日计划
- 日报摘要

【Market Phase】

将整个窗口划分为少数真正有意义的市场阶段。

120天通常只应有4～8个主要阶段。

只有风险偏好、成交、市场广度、风格、主线或市场级风险发生显著变化时才切换阶段。

不要按每天划阶段。

【Story】

识别窗口内真正重要的 Story。

是否进入全景，不取决于今天是否活跃。

即使现在已经退潮，只要它曾主导市场、形成显著赚钱效应、持续较长、影响风险偏好或发生多轮行情，都必须保留。

不要只保留 Active Story。

【Episode】

同一 Story 可以有多轮独立行情。

上一轮已经退潮，后来因为新的变量重新启动，必须创建新 Episode。

禁止把多轮行情写成一条连续行情。

【大型母题与 Subtheme】

对 AI、医药等大型母题，必须识别内部主要承载分支的先后变化。

例如如果数据中存在：
芯片、CPO、PCB、存储、液冷、PTFE、超节点、AI应用，

必须讲清：
- 哪个先出现
- 哪个成为容量承载
- 哪个后来退潮
- 哪个新分支接棒
- 是母题结束还是内部轮动

不要只描述最后几天。

【Style Evolution】

不要只生成“当前资金偏好”。

必须分析整个窗口中：
- 大票/小票
- 趋势/连板
- 高位/低位
- 容量/高价格反应
- 10cm/20cm/30cm
- 成长/防御/周期
- 主线集中/快速轮动

如何随时间变化。

【Turning Point】

只保留真正改变后续市场理解的重要节点。

每个节点回答：
1. 转折前是什么状态？
2. 实际发生了什么？
3. 为什么不是普通波动？
4. 后面市场因此怎样改变？

【Story Interaction】

分析故事之间的接力、竞争、共振和相对强化。

不得臆测真实账户资金从A流入B。

只能依据盘面描述市场重心变化。

【Window Pattern】

提炼3～8条仅由本窗口真实历史反复支持的规律。

不要复制通用交易格言。

【当前】

当前只作为整个历史的终点。

不能占全文主体。

【输出】

只输出符合 MarketPanoramaHistory Schema 的严格 JSON。

不要输出 Markdown。
不要补造历史。
不要让最近3～5天的信息吞掉窗口早期和中期的重要历史。
```


# 19. 每日增量更新逻辑 V2

禁止：

```text
昨日市场全景文章 + 今日日报 → 新文章
```

这会形成递归摘要和历史漂移。

每日正确流程：

```text
昨日 market_panorama_history.json
+ 今日独立复盘
+ 可选最近3～5日原始复盘
        ↓
更新结构化历史模型
        ↓
新的 market_panorama_history.json
        ↓
重新渲染整个市场全景文章
```

## 19.1 每日更新步骤

1. 滚动120天窗口。
2. 判断今日是否改变当前 Market Phase。
3. 更新 Story / Episode。
4. 更新大型母题内部 Subtheme。
5. 必要时结束旧 Episode / 开新 Episode。
6. 判断是否形成新的 Turning Point。
7. 更新 Style Evolution。
8. 更新 Story Interaction。
9. 必要时调整 Window Pattern。
10. 更新很短的 Window End State。
11. 重新渲染整篇市场全景。

绝大多数普通交易日：

> **不应该新建 Market Phase，也不应该新建 Turning Point。**


# 20. 每日增量 Prompt V2

```text

- 延续原有阶段

- 推进某个 Story
- 结束某个 Episode
- 开启新的 Episode
- 改变某个母题内部的主要承载分支
- 构成新的真正 Turning Point
- 改变风格演进理解

【历史连续性】

不得因为今天某方向很强，就让它吞掉过去几十天的重要故事。

不得因为某故事今天退潮，就把它从120天历史删除。

【Subtheme】

对于AI、医药等大母题，优先判断：

不要因为CPO弱、液冷强，就机械结束AI。

【Turning Point】

Turning Point 是稀缺事件，普通轮动不是 Turning Point。

【Style Evolution】

只有连续证据或强市场级变量支持时才新增节点。

【Window Rolling】

默认最近120个自然日。

历史不足120天则保留全部已有历史。

【输出】

只输出更新后的 MarketPanoramaHistory JSON。
不要输出 Markdown。
不要把“今日变化”当成市场全景正文。
不要删除窗口内仍重要的历史。
```

# 21. 市场全景叙事渲染 Prompt V2

```text
你是一名成熟的A股市场复盘作者。

输入是一份结构化的 market_panorama_history.json。

请把它写成一篇真正可读的“市场全景”。

标题只能是：

# 市场全景

不要在标题中添加“近120日”“市场演进”“交易日”等字样。

标题下可以注明：
默认观察最近120天；若历史不足，则注明实际覆盖区间和交易日数量。

【核心写作目标】

这不是数据报告。

这是：

“站在今天，给一个交易者完整讲清楚最近这一段市场是如何一步一步走到今天的。”

用户每天都复盘，因此不要把篇幅浪费在复述最近一两天。

真正需要帮助用户恢复的是：
- 更早阶段
- 主线演进
- Story生命周期
- 风格变化
- 市场转折
- 不同故事之间的接力关系

【固定结构】

## 1. 过去这段时间，市场走了一条什么路
连续自然语言概括整个窗口。不要表格，不要当前状态卡。

## 2. 市场阶段演进
按时间顺序讲主要阶段：环境、风险偏好、风格、故事、为何进入下一阶段。

## 3. 主要市场故事演进
按整个窗口的重要程度排序，不按当前强弱。
每个 major story 单独成节。
大型母题必须按历史顺序讲内部子主题。
已经退潮但曾重要的 Story 也必须完整写。

## 4. 资金风格的演进
讲清大/小、趋势/连板、高/低、容量/高价格反应、10cm/20cm/30cm、成长/防御/周期、主线集中/轮动如何变化。

## 5. 最重要的市场转折点
选真正重要节点，写成：此前 → 发生 → 改变 → 后续。

## 6. 主线之间如何接力、竞争和共振
不要把每个Story写成彼此孤立的积木。

## 7. 回头看，这段市场反复出现了什么规律
仅总结输入历史真正支持的规律。

## 8. 截至窗口末端，我们现在走到了哪里
简短收尾，只占全文5%～10%。

【文风】

必须：
- 连贯
- 有叙事
- 有时间感
- 有转折
- 有因果，但区分事实与推断
- 像专业交易者给另一个交易者讲市场

禁止大量使用：
- 状态：
- Priority：
- 正向证据：
- 负向证据：
- 下一验证：
- 核心传感器：
- 当前赚钱效应：
- 当前亏钱效应：
- 本次更新：

后台字段必须转化成自然语言。

不要让文章变成数据库字段拼装。

【篇幅建议】

总叙事：8%～12%
市场阶段：20%～25%
主要故事：35%～45%
风格演进：10%～15%
转折与接力：10%～15%
规律：5%～10%
窗口末端：5%～10%

最重要：
不要让最近3天占据整篇文章。
如果历史只有16个交易日，也要从最早一天开始完整讲，而不是只放大最后一天。
```


# 22. 近期偏差防护

模型天然容易过度关注最后几份复盘。

必须增加检查。

例如：

```json
{
  "coverage_check": {
    "early_window_story_coverage": true,
    "middle_window_story_coverage": true,
    "late_window_story_coverage": true
  }
}
```

若历史已有120天，而最终文章：

- 最近10天占全文70%
- 早期重要故事几乎消失
- 已退潮的 major Story 被省略

则视为质量失败。

3. Episode 历史准确性
4. Market Phase 清晰度
5. 风格演进完整度
6. Story 接力/竞争叙事
7. 是否有严重近期偏差

# 30. 验收测试

## Case 1：重要故事已退潮

医药曾连续多日主导市场，但窗口末端退潮。

正确：

> 市场全景仍完整讲医药历史。

错误：

> 因为它不 Active，所以文章几乎不提。

## Case 2：AI内部承载多次变化

正确：

> 按真实历史把 CPO、芯片、PCB、液冷、PTFE、超节点、应用连接成演进。

错误：

> 只写最后两天的AI应用和超节点。

## Case 3：农业两轮行情

正确：

> Episode 1 与 Episode 2 分开。

错误：

> 从第一次启动一直持续至今。

## Case 4：最后一天特别精彩

正确：

> 仍只是历史末端。

错误：

> 一篇120天全景70%都在写最后一天。

## Case 5：当前最强与历史最重要不同

正确：

> 按整个窗口重要性安排篇幅。

错误：

> 当前最强永远排第一、占最大篇幅。

## Case 6：Market Phase

正确：

> 120天划分约4～8个大阶段。

错误：

> 120天划成20多个阶段。

## Case 7：文风

正确：

> 连续历史叙事。

错误：

> 状态 / 证据 / 负面 / 下一验证 的机器卡片。

# 32. 最终设计原则

1. **功能名字永远叫“市场全景”。**
2. **默认窗口120天。**
3. **市场全景是120天市场演进史，不是当前状态卡。**
4. **纵轴是市场阶段，横轴是重要故事。**
5. **今天只是历史末端，不是全文中心。**
6. **已退潮但曾经重要的 Story 必须保留。**
7. **Story 是长期故事，Episode 是一轮独立资金周期。**
8. **大型母题必须讲内部承载分支如何迁移。**
9. **后台结构化，前台自然叙事。**
10. **禁止把数据库字段直接渲染成文章。**
11. **每日增量更新结构化历史，定期从原始复盘全量重建。**
12. **市场全景的价值是帮助用户恢复记忆、理解主线演进和市场阶段变化。**
13. **一篇好的市场全景读完后，用户应该能回答：过去这几个月，市场究竟是怎么一步一步走到今天的？**
