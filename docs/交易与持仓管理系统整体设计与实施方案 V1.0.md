# 交易与持仓管理系统整体设计与实施方案 V1.0

> 面向个人 A 股中期交易  
> 目标：TradePlan → 模拟交易 → 执行管理 → 持仓管理 → 退出 → 复盘 → 后续无缝接入实盘

---

# 1. 本文档目的

当前项目已经基本实现 `TradePlan`，但 TradePlan 依赖账户资金、当前仓位、风险配置等上游数据，仅作为孤立功能无法进行完整测试。

因此后续不再继续孤立开发某一个页面，而是建立完整的：

**交易与持仓管理系统**

系统首先服务于券商/QMT模拟账户，经过一段时间真实仿真使用后，再切换至真实账户。

本系统不是：

- 自动选股系统；
- 全自动量化策略；
- 高频交易系统；
- 机构级 OMS；
- 机构级风控平台。

它定位为：

> **人工完成投资判断，系统负责账户管理、交易计划、风险与仓位计算、专业订单执行、订单跟踪、持仓管理和交易记录。**

---

# 2. 核心设计原则

## 2.1 人负责决策，系统负责计算和执行

用户负责：

- 选择股票；
- 判断是否值得交易；
- 判断入场区域；
- 判断风险参考位置；
- 判断是否加仓、减仓、退出；
- 决定是否采用某种执行方式。

系统负责：

- 计算仓位；
- 计算计划风险；
- 检查账户约束；
- 生成订单；
- 执行已经批准的规则；
- 管理订单状态；
- 跟踪成交；
- 更新持仓；
- 保存交易全过程。

---

## 2.2 模拟与实盘必须使用相同领域模型

不要分别开发：

```text
虚拟交易系统
真实交易系统
```

统一为：

```text
Trading System
        │
        ▼
Broker Gateway
        │
        ├── SIM ACCOUNT
        └── LIVE ACCOUNT
```

正常情况下从模拟切换实盘，不应该修改：

- TradePlan；
- ExecutionPlan；
- Order；
- Fill；
- Position；
- Risk；
- UI主要流程。

只更换账户和 Broker Adapter。

---

# 3. 关于模拟交易的重要决策

正式模拟交易不由本项目自行实现撮合。

优先使用：

> **券商/QMT模拟柜台**

未来国投证券迅投权限开通后接入。

迅投官方文档本身支持模拟账号，并提供交易函数、行情、委托与成交回报等完整接口。真正发送模拟/实盘柜台委托需要进入模型交易环境。

因此：

## 不开发

```text
最低价 <= 委托价
→ 本地程序假定成交
```

这种正式模拟撮合逻辑。

原因是无法真实模拟：

- 排队；
- 部分成交；
- 市价委托；
- 撤单；
- 盘口流动性；
- 柜台拒单；
- 交易所规则。

---

# 4. 券商尚未接入期间的临时模式

为了让 TradePlan 和其他页面现在就能够开发和测试，引入：

## PLANNING_ACCOUNT

中文显示：

> 规划账户

它不是“模拟盘”。

仅提供：

```text
初始资产
可用现金
已有持仓
当前市值
风险配置
```

用于：

- TradePlan计算；
- 页面开发；
- 仓位逻辑验证；
- Position页面测试；
- ExecutionPlan页面测试。

规划账户允许开发者或用户手工维护数据。

但：

> 不负责模拟成交。

真正模拟交易必须切换至：

```text
SIM_ACCOUNT
```

并由券商/QMT模拟柜台提供成交结果。

# 5. 专业概念模型

系统内部使用以下核心概念。

---

## 5.1 TradingAccount

交易账户。

负责描述：

> 我现在有多少钱、多少现金、持有哪些证券。

账户类型：

```text
PLANNING
SIMULATION
LIVE
```

---

## 5.2 RiskProfile

账户交易风险规则。

回答：

> 我允许自己承担多大的仓位和风险？

例如：

```text
默认单笔计划风险%
单笔绝对最大风险%
单只证券最大仓位%
账户最大总仓位%
```

RiskProfile 是规则。

TradingAccount 是当前事实。

二者必须分离。

---

## 5.3 TradePlan

已经实现。

回答：

> **这笔交易我想怎么做？**

核心包括：

```text
参考入场
最高接受入场
风险参考价格
计划风险
目标
建议仓位
人工计划仓位
```

TradePlan 不负责发订单。

---

## 5.4 ExecutionPlan

中文：

> **执行计划**

这是 TradePlan 和真实 Order 之间非常重要的一层。

回答：

> **已经决定要买，那么具体准备怎么完成这次买入？**

例如：

```text
买1000股 XX股票

方式：
限价

价格：
不高于10.20

有效期：
5个交易日

未成交：
下一交易日继续

部分成交：
继续完成剩余数量
```

或者：

```text
价格进入9.90~10.00
→ 触发买入

触发后：
对手方最优
```

ExecutionPlan 表达的是持续性的“执行意图”。

---

## 5.5 Order

订单 / 委托。

是某一次真正发送到券商柜台的委托。

例如：

```text
2026-09-02
BUY 600xxx
1000股
LIMIT 10.00
```

ExecutionPlan 可以产生多个 Order。

例如：

```text
持续5天买1000股

Day 1：
Order #1

未成交

Day 2：
Order #2

成交300股

Day 3：
Order #3
剩余700股
```

---

## 5.6 Fill

成交。

Order ≠ Fill。

例如：

```text
订单：
1000股

成交：
300 @ 10.00
200 @ 9.99
500 @ 9.98
```

应保存3条 Fill。

---

## 5.7 Position

持仓。

由真实成交形成。

负责：

```text
数量
可卖数量
平均成本
当前价
市值
浮盈亏
账户仓位
当前人工风险参考位置
```

# 6. OMS 与 EMS 的专业定位

系统逻辑上同时包含 OMS 与 EMS，但不建设机构级独立平台。

## OMS —— 订单管理

解决：

```text
订单发出去了吗？
券商接受了吗？
成交多少？
剩多少？
撤单成功了吗？
有没有重复订单？
```

## EMS —— 交易执行

解决：

```text
我到底应该怎样完成这1000股交易？
```

包括：

- 限价；
- 市价类申报；
- 条件执行；
- 持续执行；
- 分批执行；
- TWAP等算法执行。

实现上两者仍处于同一个 Trading 模块。

不要建设微服务。

# 13. PreTrade Risk

这是后台能力，不需要独立页面。

每次准备产生真实 Order 前执行。

至少检查：

```text
账户是否可交易

ExecutionPlan是否ACTIVE

TradePlan是否有效

计划是否超过有效期

当前证券是否已有重复订单

计划剩余数量是否 > 0

可用现金是否足够

单股仓位是否超过上限

总仓位是否超过上限

预计计划风险是否超过硬限制

当前价格是否超过TradePlan允许范围

证券当前是否允许交易

订单数量是否合法
```

输出：

```text
PASS

WARNING

BLOCK
```

其中：

> TradePlan负责计划时风险计算。

> PreTrade Risk负责订单发出的这一刻重新检查现实情况。

# 15. 专业交易执行的正确分类

这是系统以后非常重要的设计。

不要把所有东西都称为：

> “订单类型”。

交易执行至少分成三个层次。

---

# 16. 第一层：交易所/券商原生订单

例如：

## LIMIT

限价申报。

这是最常用的基础类型。

---

## Market-style Orders

包括交易所规定的市价申报方式。

2026年上交所现行规则包括：

- 最优五档即时成交剩余撤销；
- 最优五档即时成交剩余转限价；
- 本方最优；
- 对手方最优等。

深交所现行规则包括：

- 对手方最优；
- 本方最优；
- 最优五档即时成交剩余撤销；
- 即时成交剩余撤销；
- 全额成交或撤销等。

因此：

**系统不能写死所有股票都拥有完全相同的订单类型。**

---

# 17. BrokerCapabilities

Broker连接后必须返回能力描述。

例如：

```text
BrokerCapabilities

native_orders:
    LIMIT
    COUNTERPARTY_BEST
    SAME_SIDE_BEST
    FIVE_LEVEL_IOC
    FIVE_LEVEL_TO_LIMIT

conditional_execution:
    PRICE_TRIGGER
    PRICE_RANGE
    TIME_TRIGGER

algorithms:
    TWAP
    VWAP
```

UI根据：

```text
证券市场
+
账户权限
+
券商能力
```

动态显示可用选项。

不要因为QMT文档存在某功能就直接假定国投账户一定支持。

---

# 18. 第二层：条件执行 Conditional Execution

这是个人交易非常有价值的一层。

它不是交易所订单类型。

例如：

## PRICE_TRIGGER

```text
当价格 <= 10.00
触发买入
```

## PRICE_RANGE

```text
只有进入
9.90 ~ 10.00

才触发
```

## TIME_TRIGGER

```text
10:30以后执行
```

## Persistent Limit

例如：

```text
目标：
买1000股

最高：
10.00

有效：
5个交易日

今天没成交：
明日继续

部分成交：
继续剩余数量
```

交易所实际订单通常仍然是“当日订单”。

持续执行由系统保存 ExecutionPlan，并在下一交易日继续生成新的 Order。

---

# 19. 第三层：算法执行

例如：

```text
TWAP
VWAP
ICEBERG
```

迅投官方 API 当前公开支持 TWAP、VWAP、跟量、跟价、盘口、冰山等智能算法参数。

但本项目的重要原则是：

> **优先调用 Broker/QMT 原生算法，不自己实现专业算法撮合。**

因为算法执行依赖：

- 实时行情；
- 盘口；
- 成交量；
- 交易时段；
- 委托反馈。

如果 QMT 已提供成熟实现，没有必要重新造轮子。

---

# 20. V1真正应该支持的执行方式

第一批正式支持：

### 1. 限价委托

必须。

### 2. 修改未完成订单

UI显示：

> 修改订单

后台实现：

```text
撤销原订单
↓
确认已成交数量
↓
取得真实剩余数量
↓
重新发送新订单
```

即专业意义上的：

> Cancel / Replace

用户不用自己撤单再重新计算剩余股数。

### 3. 持续限价执行

例如：

> 10元以下持续买1000股，5个交易日有效。

### 4. 价格触发

例如：

> 跌到10元以后才启动买入。

### 5. 价格区间触发

例如：

> 9.90~10.00才允许启动。

这五个能力对于个人中期交易已经非常实用。

---

# 21. 第二批执行方式

Broker接入并稳定后增加：

```text
对手方最优
本方最优
五档即时成交类
```

目的之一就是让用户能够在模拟账户中学习这些真实交易方式。

# 26. client_order_id

必须由本系统产生唯一 ID。

目的：

```text

```

# 52. 最终产品判断标准

这个交易系统不是以：

> “功能够不够专业”

来衡量。

也不是以：

> “代码是不是最少”

来衡量。

最终标准是：

### 专业概念不能错

例如：

```text
TradePlan ≠ Order

ExecutionPlan ≠ Order Type

Order ≠ Fill

持仓 ≠ TradePlan

市价申报 ≠ 条件单

TWAP ≠ 交易所订单类型
```

### 实际使用不能复杂

正常一次交易应该是：

```text
选股票
↓
填写TradePlan
↓
看系统计算
↓
选择执行方式
↓
确认
↓
系统管理订单
↓
形成持仓
```

### 能交给程序的机械工作不让用户重复做

例如：

```text
撤单后重挂
计算剩余数量
第二天继续执行
跟踪部分成交
同步持仓
风险重新检查
```

### 投资判断仍由用户掌握

例如：

```text
买哪只股票
为什么买
风险位置在哪里
是否加仓
趋势是否破坏
什么时候退出
```

这就是本项目“个人专业交易系统”的长期边界。
