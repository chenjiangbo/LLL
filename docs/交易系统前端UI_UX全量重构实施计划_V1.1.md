## 1. 本次目标与边界

本次重构将交易系统的 13 个页面逐页用 React 重新实现，视觉、字体、间距、层级、状态和交互以现有界面原型为验收基准，同时保留并复用上一版已经完成的后台接口对接和业务能力。

新页面的正式源码只放在 `frontend`，原型目录只作为设计参考和视觉对照，不作为运行时源码目录。新页面不得通过 iframe、`DOMParser`、`innerHTML`、整段 HTML 注入或把原型页面套进 React 的方式实现。

数据库当前不可用，因此本阶段先完成源码结构、页面实现计划和不依赖数据库的静态检查；数据库恢复后再进行真实账户、订单、持仓、执行计划和交易链路验收。本计划不以伪数据或静默降级替代核心数据链路。

“账户敞口与技术分级监控快照”不是现有交易后台接口或业务设计文档定义的核心功能，属于原型中的策略执行可视化占位区域。本次已从交易总览正式页面删除，后续 13 页重构中不再实现该模块。

## 3. 总体技术方案

### 3.1 页面层级

- `TradingSystemShell` 只负责账户选择、左侧导航、页面路由和全局交易状态，不负责拼接原型 HTML。
- 每个业务页面拥有独立的 React 组件和明确的数据适配层。
- 抽取统一的页面框架、标题区、状态标签、金额/比例格式化、表格、空状态、错误状态、确认操作和审计时间线组件。
- 页面展示状态必须来自现有接口；加载、空数据、权限不足、接口错误分别显示明确的业务状态。

建议的公共组件目录：

```text
frontend/app/components/trading/
├── common/                 # 页面框架、表格、状态、格式化、错误/空状态
├── overview/
├── trades/
├── trade-detail/
├── action-plans/
├── risk-reference/
├── actions/
├── execution/
├── orders/
├── positions/
└── settings/
```

### 3.2 数据原则

- 继续使用上一版已经打通的交易、账户、订单、成交、持仓、执行计划和券商状态接口。
- 不在核心数据链路中增加 mock、样例数据、固定数量截断、静默 fallback 或“接口失败仍显示成功”的逻辑。
- 账户必须隔离：切换账户后重新读取对应账户的概览、实时快照、订单、成交和持仓。
- 实时账户以实时快照为事实来源；计划中账户只展示计划态数据，并在界面上区分数据状态。
- 待办事项可以保留 2～3 条用于视觉验收，但这只是总览页面的展示预览，不删除或截断后台事实记录；数据库恢复后必须用真实待办链路复核执行计划、订单和对账结果。

### 3.3 K 线统一方案

所有涉及 K 线的页面必须复用项目现有实现，不使用原型里的假 K 线、静态 SVG、图片或 HTML 图表：

- `frontend/app/components/KLineModal.tsx`：用于 Trade 详情、风险参考、持仓及需要弹窗查看行情的页面。
- `frontend/app/components/TradePlanKLinePanel.tsx`：用于建仓、加仓、减仓、清仓等计划页面中的嵌入式 K 线和价格选择。
- K 线数据继续调用现有 `/api/screening/kline/...` 接口，并传入真实证券代码、名称、周期和时间范围。
- 接口无数据时显示“暂无行情数据”及可复核的错误状态，不回退到原型截图或假数据。
- 每个使用 K 线的页面完成后，必须验证证券上下文没有串号、周期切换有效、时间与价格字段来自真实响应。

## 4. 页面实施要求

### 4.1 交易总览

按 `_1` 原型复刻：第一行 4 个主卡片；风险区域左侧为风险提示，右侧为两个小卡片；Trade 列表同时显示运行中和计划中；待办事项最多展示 2～3 条不同状态样式；最近系统动作采用原型时间线结构。删除“账户敞口与技术分级监控快照”。继续对接概览、实时快照、券商连接和交易接口。

### 4.2 交易列表与 Trade 详情

交易列表按原型实现筛选、状态标签、搜索、分页和行级操作，必须区分计划、运行中、退出中、已完成和已取消。Trade 详情展示交易生命周期、持仓汇总、风险参考、腿级信息、退出规则和关联动作；点击真实证券时使用现有 K 线组件。

### 4.3 建仓、加仓、减仓、清仓

四类动作共用计划表单、行情上下文、数量/价格/风险计算和提交确认能力，但按原型保留各自字段和文案。数量、T+1、风险参考、最小可接受价、触发条件和原因必须来自真实计算接口或用户输入；计算失败不能静默显示旧值。K 线使用 `TradePlanKLinePanel` 或 `KLineModal`，不使用原型假图。

### 4.4 风险参考与动作详情

风险参考页展示当前参考值、调整记录、触发条件和关联 Trade；动作详情展示动作状态、执行进度、订单/成交关联和审计信息。所有状态必须可追溯到 Trade、Action、Order 或 Fill 数据。

### 4.5 执行计划、订单、持仓

执行计划页展示待执行和执行中的计划、进度、数量、价格、方式、有效期及失败原因；订单页展示委托、成交、撤单和错误状态；持仓页展示账户汇总、数量、可用数量、T+1、成本、盈亏、敞口和关联 Trade。三页不得用原型中的静态数量覆盖真实接口结果。

### 4.6 配置（保留）

本页不参与本轮视觉重构，继续使用已经调通的 React `SettingsPage`。不得替换其券商账户、连接状态、风险设置、交易控制和数据管理交互；本轮只确认它没有被新交易页面的迁移改坏。

## 10. 数据库恢复后的联调与验收计划

数据库恢复后，前端不需要重新开发页面，按以下顺序完成真实数据联调。所有步骤必须在前一步通过后再进入下一步；核心接口失败时直接记录错误并停止该步骤，不使用伪数据、静默跳过或 fallback 数据掩盖问题。

### 10.1 环境与数据链路恢复

1. 确认 PostgreSQL、后端 API、Broker Node（如本地环境需要）和前端服务的实际运行状态；记录服务地址、账号上下文和启动日志。
2. 检查前端 `NEXT_PUBLIC_MARKET_REVIEW_API_URL` 是否指向当前后端，不通过读取不到环境变量再切换其他地址的方式启动。
3. 逐项请求交易总览、Trade、持仓、执行计划、订单、成交、风险参考、退出规则和对账接口，确认 HTTP 状态、账号隔离和响应结构。
4. 做数据支撑性校验：接口总量、关键字段、账号 ID、Trade/ExecutionPlan/Order/Fill 关联关系和持仓汇总必须能够相互解释；缺失字段要在页面显式显示或报错。

### 10.2 交易总览页面验收

数据库恢复后只验收交易总览页面，其他交易页面不安排真实数据联调、写入操作验证或截图验收。总览页验收范围如下：

1. 确认当前账号和券商连接状态来自真实接口，账号 ID 没有串用。
2. 核对第一行四个主卡片：账户净资产、可用现金、当前总仓位、账户当前总风险。
3. 核对风险提示条及右侧两个小卡片，确认账户敞口、风险预算和数据缺失状态有明确业务表达。
